# Wiring the pi → bb event bridge

bb 0.39.0's `provider-pi` embeds the Pi coding agent in-process inside a
host-daemon **bridge worker** (`bb-provider-bridge-worker.mjs` →
`bb-pi-bridge.mjs`). That worker never set `BB_BRIDGE_SOCKET_PATH`, so the
`pi-bb-bridge` extension (env-gated on that variable) stayed a no-op and no pi
events ever reached `bb-plugin-pi-events-bridge`.

This repo fixes it in two parts, both verified end-to-end:

1. **The chokepoint publishes its connection info** to a well-known file.
2. **A patch makes the bridge worker export that info into the pi environment**
   before any session is created.

## Install steps

### 1. Install the pi extension

```sh
cp packages/pi-bb-bridge/index.ts ~/.pi/agent/extensions/pi-bb-bridge.ts
```

The embedded pi discovers `~/.pi/agent/extensions/*.ts` on every session start
(via the resource loader's auto-discovery). The extension is a no-op unless
`BB_BRIDGE_SOCKET_PATH` is set, so it is safe to leave installed.

### 2. Apply the bridge patch

```sh
node scripts/patch-pi-bridge.mjs
```

This locates `bb-pi-bridge.mjs` (next to the `bb` binary on PATH, or in the npx
cache) and idempotently inserts a module-scope snippet that reads
`<tmpdir>/bb-plugin-pi-events-bridge.json` (written by the chokepoint on every
load) and sets `BB_BRIDGE_SOCKET_PATH` / `BB_BRIDGE_TOKEN` in the worker
environment unless already set. Explicit env vars win.

- Idempotent: re-running prints `already patched`.
- Revert: `node scripts/patch-pi-bridge.mjs --revert` (restores the file
  byte-for-byte).
- **Re-apply after every bb update** (the npx cache path changes and the file
  is replaced).

### 3. Restart bb / the provider workers

Bridge workers load `bb-pi-bridge.mjs` at process start, so **long-lived
workers keep the unpatched behavior until they are recycled**. A full bb
restart (or waiting for the daemon to recycle idle workers) is required for
real user sessions to pick up the wiring. Fresh workers (e.g. the provider
maintenance runtime) pick it up immediately.

## How it works

```
bb-pi-bridge.mjs (patched)
   │  reads <tmpdir>/bb-plugin-pi-events-bridge.json
   ▼  sets process.env.BB_BRIDGE_SOCKET_PATH / BB_BRIDGE_TOKEN
embedded pi session (createAgentSessionServices)
   │  loads ~/.pi/agent/extensions/pi-bb-bridge.ts
   ▼  connects to the Unix socket, sends bb.bridge:hello
bb-plugin-pi-events-bridge (chokepoint)
   • ring-buffers per pi session, re-emits on bb.realtime
   • exposes rpc.status / rpc.recent / rpc.sessions / rpc.threadSession
   • writes <tmpdir>/bb-plugin-pi-events-bridge.json on load
   └── consumers (pi-subagents-fleet, pi-codex-goal, mcp-mediator) poll
```

The `<tmpdir>/bb-plugin-pi-events-bridge.json` file is the contract between the
two sides:

```json
{ "socketPath": "/tmp/bb-plugin-pi-events-bridge-pi-events-bridge.sock",
  "token": "<auto-generated hex>", "requiresAuth": false, "pid": 1234,
  "updatedAt": "..." }
```

`requiresAuth` is `false` unless the plugin setting `authToken` is set; the
patch exports the token anyway so enabling auth later requires no re-patch.

## Verification

With the chokepoint reloaded (`bb plugin reload pi-events-bridge`), inspect
live state:

```sh
# thread → pi session map
curl -s http://127.0.0.1:38886/api/v1/plugins/pi-events-bridge/http/threads
# sessions, connected sockets, listening state
curl -s http://127.0.0.1:38886/api/v1/plugins/pi-events-bridge/http/status
```

End-to-end (proven during development): with the env vars set, an embedded pi
session (via `createAgentSessionServices` + `createAgentSessionFromServices`)
connected, sent `bb.bridge:hello`, then forwarded `pi.lifecycle:session_start`
and third-party events such as `pi.ext:pi-mcp-adapter/status/v1` — visible as
separate per-cwd sessions in `/status` with `eventCount > 1`.

After a bb relaunch (fresh bridge workers), a real thread forwarded **37+ events**
keyed by its session id (`thr_<id>`), and a `/goal` thread's objective showed up
in `bb-plugin-pi-codex-goal` with status `active` and a history — the full
pi → chokepoint → consumer path.

### Session id & goal capture

- The extension emits `sessionId` as a **top-level** wire field (the chokepoint
  keys sessions by it); the value is the session file basename, which for bb
  threads equals the thread id (`thr_<id>`), so per-thread views work without a
  separate provider mapping.
- `ThreadResponse.providerThreadId` is null for pi, so the chokepoint's
  thread→session map falls back to the thread id itself.
- Embedded (RPC) runtimes never emit `context` events, so goal state is read
  directly from `ctx.sessionManager.getEntries()` on `session_start`,
  `turn_start`, `turn_end`, and `agent_settled`, and synthesized into
  `pi.ext:codex-goal/entry` + `pi.ext:codex-goal/state` envelopes (deduped by
  entry fingerprint).

## Also fixed: socket-reload race

`bb-plugin-pi-events-bridge/server.ts` previously raced reloads: the stale
socket *file* kept the path bound (`EADDRINUSE`), and an ill-advised
`unlinkSync` in `onDispose` could delete the *new* server's socket file after a
late connection closed. Current behavior:

- `EADDRINUSE` on bind → unlink the stale file, retry (up to 5×, 150ms).
- `onDispose` only `close()`s — never unlinks (the kernel releases the inode).
- A `bound` flag dedupes Node's double `listening` callback on retried binds.
- A `GET /status` HTTP route exposes live state for debugging.
